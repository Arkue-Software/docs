# 2.3 Cuadrante 1 - Lenguajes y Frameworks

| #   | Herramienta                 | Anillo  | Descripción y uso                                                                                            | Justificación                                                                                                                                     |
| --- | --------------------------- | ------- | ------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Java (LTS)                  | Adoptar | Lenguaje del backend. Se usa para toda la lógica de negocio del sistema.                                     | Es la tecnología con mayor dominio en el equipo. Su tipado estático reduce errores en un dominio donde la trazabilidad de cada unidad es crítica. |
| 2   | Spring Boot                 | Adoptar | Framework del backend. Estructura los servicios backend, expone APIs REST y gestiona la inyección de dependencias. | Estándar de facto en desarrollo empresarial. Permite desacoplar el sistema en servicios distribuidos de manera modular.                           |
| 3   | Spring Data JPA / Hibernate | Adoptar | Mapeo objeto-relacional. Traduce el modelo de dominio a tablas de la base de datos.                          | Su soporte de herencia y polimorfismo habilita el requerimiento M9 de extensibilidad del dominio hacia otros tipos de donación.                   |
| 4   | Spring Security             | Adoptar | Autenticación y autorización. Controla qué puede ver y hacer cada rol.                                       | Resuelve de forma nativa el RNF-02: permite restringir por rol y por alcance territorial sin construir el mecanismo desde cero.                   |
| 5   | Spring Scheduler            | Adoptar | Ejecución de tareas programadas de forma periódica.                                                          | Cubre el RNF-08 (retiro automático de unidades vencidas) y el RF-15 (expiración de reservas) coordinando bloqueos distribuidos para evitar ejecuciones duplicadas. |
| 6   | TypeScript                  | Adoptar | Lenguaje del frontend.                                                                                       | Añade tipado a JavaScript, lo que reduce errores de integración con las APIs del sistema distribuido. El equipo ya lo maneja.                    |
| 7   | React                       | Adoptar | Biblioteca de interfaz de usuario. Construye los paneles de donante, banco de sangre y entidad territorial.  | Experiencia previa del equipo y modelo de componentes que permite reutilizar elementos entre los tres perfiles de usuario.                        |
| 8   | Tailwind CSS                | Probar  | Framework de estilos por utilidades.                                                                         | Acelera la construcción de interfaces consistentes sin escribir CSS desde cero. Se prueba en un módulo antes de generalizar.                      |
| 9   | Spring @Async + reintentos  | Probar  | Ejecución asíncrona de notificaciones en segundo plano a nivel de nodo.                                      | Cubre la asincronía básica de notificaciones (RNF-06) dentro de los servicios sin requerir de entrada infraestructura de mensajería compleja.    |

| 13  | Flyway                            | Probar  | Versionado y migración del esquema de base de datos.                                                                                                       | Permite que los cambios de esquema viajen con el código y sean reproducibles en los diferentes nodos o bases de datos del sistema.                                                    |

# 2.6 Cuadrante 4 - Técnicas y Prácticas

| #   | Práctica              | Anillo  | Descripción y uso                                                                                                                                                           | Justificación                                                                                                                                                                                                 |
| --- | --------------------- | ------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 58  | Scrum                 | Adoptar | Marco de trabajo del equipo: sprints semanales, ceremonias y roles definidos.                                                                                               | Marco exigido por el curso y adecuado a un alcance que se refina entrega a entrega.                                                                                                                           |
| 59  | Modelo C4             | Adoptar | Documentación de la arquitectura en niveles de contexto, contenedores y componentes.                                                                                        | Permite comunicar la arquitectura distribuida a audiencias técnicas y no técnicas con el mismo conjunto de diagramas.                                                                                        |
| 60  | ADR                   | Adoptar | Registro estructurado de cada decisión arquitectónica relevante.                                                                                                            | Deja trazabilidad del porqué de cada decisión (incluyendo la transición a una arquitectura distribuida). Se produce en la Mesa de Arquitectura.                                                              |
| 61  | MoSCoW                | Adoptar | Priorización del alcance en Must, Should, Could y Won't.                                                                                                                    | Con 5 sprints, hace explícito qué se corta primero si la capacidad no alcanza.                                                                                                                                |
| 62  | Monolito modular      | Evitar  | Aplicación única desplegable, con separación interna por módulos.                                                                                                           | Descartado: entra en conflicto directo con la restricción de diseño que exige una arquitectura distribuida.                                                                                                    |
| 63  | Pruebas automatizadas | Probar  | Pruebas unitarias y de integración sobre la lógica crítica.                                                                                                                 | Se priorizan los escenarios de confidencialidad (RNF-01) y control de acceso (RNF-02), no la cobertura total.                                                                                                 |
| 64  | Microservicios        | Adoptar | Descomposición del sistema en servicios desplegables e independientes.                                                                                                      | Se adopta directamente para dar cumplimiento a la restricción de diseño que obliga a disponer de un sistema distribuido.                                                                                      |
| 65  | Pair Programming      | Adoptar | Técnica de desarrollo colaborativo donde dos programadores trabajan juntos en una sola estación de trabajo, alternando la escritura de código y la revisión en tiempo real. | Adoptar: Mejora significativamente la calidad del código y acelera el aprendizaje del equipo, permitiendo detectar errores al instante y transferir conocimiento de forma continua entre los desarrolladores. |
